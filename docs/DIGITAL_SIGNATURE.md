# Digital Signature Module

Enterprise-grade **report validation** for VoltHub. Every report generated by the
Enterprise Report Generator is cryptographically signed, stamped with a
**QR code**, and made **publicly verifiable** — proving the document is authentic
(issued by this system) and intact (its content has not been altered).

Applies to all report sources: **Laporan Awal**, **Laporan Akhir**, **Inspection**,
**HAR**, and therefore every **Generated Report** (PDF *and* Excel).

This feature is **additive** — it extends the `reports` module and adds one new
table (`report_signatures`). No existing behaviour changes; generation of an
unsigned report is no longer possible, but every prior endpoint keeps its shape.

> **Design constraints honoured**
> - **No external/paid services.** Signing uses Node's built-in `crypto`
>   (Ed25519). QR rendering uses the MIT-licensed, offline `qrcode` package.
> - **Works offline after PDF generation.** The signature is a self-contained
>   token embedded in the artifact's QR; it verifies against the *published
>   public key* with no server round-trip.

---

## 1. What gets produced

For each generated report the module creates:

| Artifact | Where it lives | Purpose |
|----------|----------------|---------|
| **Ed25519 signature** | `report_signatures.signature` | Cryptographic proof of authenticity |
| **Compact token** `payload.signature` | embedded in the QR + `…token` | Self-contained, offline-verifiable |
| **QR code** | last PDF page / Excel *Validasi* sheet | Scannable link to the verification page |
| **Content hash** (SHA-256) | signed, in token | Detects tampering of the report's *data* |
| **File hash** (SHA-256) | `report_signatures.fileHash` | Detects a swapped *stored file* |
| **Verification URL** | QR payload + DB | Human-openable verification page |

## 2. Cryptography

### Why Ed25519 (asymmetric), not an HMAC

An HMAC would require sharing the secret with every verifier, so it could not be
verified *publicly* or *offline* without exposing the signing key. Ed25519 is an
**asymmetric** scheme native to Node: the **private key never leaves the server**,
while the **public key is published** (`GET /verify/public-key`) so anyone —
including a fully offline third party — can validate a token. This is exactly what
makes a downloaded PDF self-verifying after the fact.

### The signed payload

A canonical (sorted-key) JSON object is what gets signed:

```jsonc
{
  "v": 1,
  "sigId": "<uuid>",            // == ReportSignature.id, == verify-page segment
  "reportNumber": "LA-20260610-AB12CD-V1",
  "sourceType": "LAPORAN_AWAL",
  "sourceId": "<uuid>",
  "version": 1,
  "contentHash": "<sha256 hex of canonical semantic content>",
  "algorithm": "Ed25519",
  "keyId": "<public-key fingerprint>",
  "issuer": "PT PLN (Persero)",
  "signedBy": "<userId|null>",
  "issuedAt": "2026-06-10T..."
}
```

### The token

```
token = base64url(canonicalPayloadJSON) + "." + base64url(ed25519Signature)
```

A JWS-style compact string. The QR encodes
`<SIGNATURE_VERIFY_BASE_URL>/verify/<sigId>?t=<token>` so a scan opens the
verification page **and** carries the self-contained token for offline checks.

### Two independent digests

- **`contentHash`** — SHA-256 over the report's *semantic* content (title, meta,
  sections). It is **signed**, so it travels inside the token and detects data
  tampering independently of file formatting. Avoids the circular dependency of
  trying to hash a file that must itself embed the hash.
- **`fileHash`** — SHA-256 of the *rendered bytes*, computed after writing and
  stored (not signed). The online endpoint re-hashes the stored file to detect a
  swapped artifact on the server.

### Keys (`signature.keys.ts`)

Resolution order (memoised):

1. `SIGNATURE_PRIVATE_KEY` / `SIGNATURE_PUBLIC_KEY` (PEM env vars) — **production**.
2. A keypair persisted under `<UPLOAD_DIR>/keys/` — generated once on first boot
   and reused (dev / self-hosted convenience).

`keyId` is the first 16 hex chars of `sha256(SPKI DER of public key)` — a stable
fingerprint that survives a future key rotation (a verifier can tell which key
signed a given token).

> **Production note:** set `SIGNATURE_PRIVATE_KEY`/`SIGNATURE_PUBLIC_KEY` to a
> fixed keypair so tokens stay verifiable across deploys and horizontally-scaled
> instances. If they are unset, each fresh filesystem gets its own keypair.

## 3. Data model

`prisma/migrations/20260610000000_digital_signature_additive` adds one table and
a 1:1 relation to `generated_reports`.

```prisma
model ReportSignature {
  id           String  @id @default(uuid())
  reportId     String  @unique          // 1:1 with generated_reports (immutable)
  reportNumber String
  sourceType   String
  sourceId     String
  version      Int     @default(1)

  algorithm   String  @default("Ed25519")
  keyId       String                     // signing-key fingerprint
  contentHash String                     // signed semantic digest
  fileHash    String                     // rendered-bytes digest (tamper check)
  signature   String  @db.Text           // base64url Ed25519 signature
  payload     String  @db.Text           // base64url canonical payload
  token       String  @db.Text           // compact self-contained token
  verifyUrl   String  @db.Text

  issuer     String
  signedBy   String?
  signerName String?

  status        String    @default("VALID")  // VALID | REVOKED
  revokedAt     DateTime?
  revokedBy     String?
  revokedReason String?

  verifyCount    Int       @default(0)        // verification telemetry
  lastVerifiedAt DateTime?

  signedAt DateTime @default(now())
  report   GeneratedReport @relation(..., onDelete: Cascade)
}
```

One **immutable** signature per generated artifact. Regenerating a report yields a
new versioned `GeneratedReport` (`…-V2`) with its own fresh signature, so prior
official copies remain independently verifiable.

## 4. Generation flow

`report.service.generate()` (every source × format):

```
load source → buildReportModel → version + reportNumber
        │
        ▼
buildSignatureArtifacts()          ← contentHash, sign, token, QR PNG   (BEFORE render)
        │
        ▼
render PDF / Excel WITH the QR + validation block embedded
        │
        ▼
fileHash = sha256(rendered bytes)
        │
        ▼
persist GeneratedReport → persist ReportSignature → audit log
```

The signature is built **before** rendering so the QR can be embedded in the
artifact. The validation block appears on a dedicated final PDF page and as a
*Validasi* worksheet in Excel — QR + issuer/signer + key fingerprint + content
hash + verify URL.

## 5. API

Base: `/api/v1`. Documented in Swagger (`/api/docs`, tag **Digital Signature**).

### Public (no authentication — QR scans must work for anyone)

| Method | Path | Purpose |
|--------|------|---------|
| GET  | `/verify/:id` | Verify a report by signature id (the QR target / verification page) |
| POST | `/verify/token` | Verify a raw compact token (e.g. pasted from a scan) — body `{ token }` |
| GET  | `/verify/public-key` | Published Ed25519 public key + fingerprint for offline third-party verification |

### Authenticated

| Method | Path | Roles | Purpose |
|--------|------|-------|---------|
| GET  | `/reports/generated/:id/signature` | any auth | Signature metadata (token, hashes, verify URL, status) |
| POST | `/reports/signatures/:id/revoke` | SUPER_ADMIN, ADMIN | Revoke a signature (superseded / issued in error) |

### Verification verdict

```jsonc
{
  "valid": true,
  "status": "VALID",            // VALID | REVOKED | TAMPERED | INVALID_SIGNATURE | NOT_FOUND
  "signatureValid": true,       // Ed25519 token authenticity
  "contentIntact": true,        // stored-file hash matches (null if file unavailable)
  "signature": { "reportNumber": "...", "issuer": "...", "signerName": "...",
                 "algorithm": "Ed25519", "keyId": "...", "signedAt": "...",
                 "revokedAt": null, "revokedReason": null },
  "report": { "title": "...", "format": "PDF", "generatedAt": "..." },
  "verifiedAt": "2026-06-10T..."
}
```

Three independent checks combine into the verdict:
1. **Token authenticity** — Ed25519 signature over the payload (offline-capable).
2. **Revocation** — `status` from the DB.
3. **File integrity** — re-hash the stored file vs the signed `fileHash`.

`status` precedence: `INVALID_SIGNATURE` → `REVOKED` → `TAMPERED` → `VALID`.
Each successful lookup bumps `verifyCount` / `lastVerifiedAt` (telemetry only).

## 6. Frontend

### Public verification page — `/verify/$id`
`FE/src/routes/verify.$id.tsx`. A branded, **unauthenticated** page (sibling of
`/login`, outside the `_app` auth shell) — the destination of every report's QR.
Shows a large VALID/REVOKED/TAMPERED verdict, authenticity & integrity badges,
and the document/issuer/signer/key details. Calls the public endpoint with a bare
`fetch` (no auth interceptors) so logged-out visitors can verify.

### Download Center integration
`FE/src/routes/_app.reports.tsx` gains a per-row **shield** action that resolves
the report's signature id and opens its verification page in a new tab.

### API client
`FE/src/features/v2/reports/signature.ts` — `useVerifySignature` (public),
`useReportSignature` (auth metadata), `useRevokeSignature`, `verifyPageUrl`.

## 7. Configuration

| Env var | Default | Purpose |
|---------|---------|---------|
| `SIGNATURE_PRIVATE_KEY` | *(empty)* | Ed25519 private key PEM (literal `\n` accepted). Empty ⇒ persisted dev keypair |
| `SIGNATURE_PUBLIC_KEY` | *(empty)* | Matching public key PEM |
| `SIGNATURE_VERIFY_BASE_URL` | `CORS_ORIGIN` | Base URL of the public verification page encoded in the QR |

Generate a production keypair:

```bash
node -e "const c=require('crypto');const{publicKey,privateKey}=c.generateKeyPairSync('ed25519');\
console.log(privateKey.export({type:'pkcs8',format:'pem'}));\
console.log(publicKey.export({type:'spki',format:'pem'}));"
```

## 8. Threat model & limitations

- **Detected:** forged documents (no valid signature), altered report data
  (content hash mismatch / signature fails), tampered stored files (file hash
  mismatch), and revoked documents.
- **Not a PAdES/eIDAS embedded PDF signature.** The signature is carried in an
  embedded QR token + a server-side record, not in a PDF `/Sig` byte-range
  dictionary. This keeps it dependency-light and format-agnostic (works for
  Excel too) while remaining offline-verifiable against the public key. A
  PAdES upgrade can be layered later without changing the data model.
- **Key custody.** Security rests on the private key. Use env-provided keys in
  production and restrict filesystem access to `<UPLOAD_DIR>/keys/`.

---

## 9. Extending

- **Rotate keys** — set new `SIGNATURE_*` env vars. Old tokens still verify via
  `keyId` so long as the old public key remains published (keep a key registry if
  rotating).
- **New report source** — nothing to do; signing is wired into the shared
  `generate()` path, so any source added to the Report Generator is signed
  automatically.
- **PAdES / embedded PDF signature** — add a post-render signing pass; the
  `ReportSignature` row already captures everything needed.
